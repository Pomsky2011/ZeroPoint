First release candidate of ZeroPoint 1.0: the fantasy-console emulator (DEF88186 CPU, PPU, APU, DMA), the real Boot ROM and the APU BIOS as binaries, and
the matching toolchain ([ZPdevtools](https://github.com/Pomsky2011/ZPdevtools) `v1.0.0-rc1`, [ZPgameTemplate](https://github.com/Pomsky2011/ZPgameTemplate) `v1.0.0-rc1`).

**Core revision 13.** Everything from here on stays compatible with revision 13: ROMs, movies (`.zpm`) and golden hashes that run on it keep running identically.
Revision 12 and earlier ROMs/movies do not replay (revision 13 stretched the raster to 4343 cycles a line, a frame is 1/60 s).

## What is in the assets

- `zeropoint-<platform>-v1.0.0-rc1.zip`: the frontends (`zeropoint_sdl`, `zeropoint_qt`) and the command-line tools, built by CI for Linux x86-64 and ARM64,
  macOS Apple Silicon and Intel, Windows x64 and ARM64. `SHA256SUMS.txt` has every hash.
- `zeropoint-bootroms-v1.0.0-rc1.zip` and `zeropoint-apu-bios-v1.0.0-rc1.zip`: **binaries only**, the Boot ROM source is not published. The binaries are in the
  **public domain (CC0 1.0)**: do anything with them, including taking them apart. Each zip says what is in it and has its own checksums. Use them with `--boot` and `--apu-bios`; without them the emulator boots through its built-in HLE Boot ROM and APU BIOS.

## Notes for this build

- Linux builds need SDL2 (and Qt 6 for `zeropoint_qt`) installed. Zips lose the executable bit: `chmod +x` the binaries after unzipping.
- macOS builds are not signed or notarized and are not `.app` bundles; clear the quarantine flag (`xattr -dr com.apple.quarantine <folder>`) to run them.
- Minimum host: 2 cores, PassMark single-thread rating of 1500.
- The Qt and SDL frontends have not been run interactively on the 1/60 s frame (the frame pacer and offscreen Qt tests pass).
- Windows and macOS runtime for the serial TCP endpoint, the Qt Serial Console and the exception flow is untested (they build on every platform).

## Known issues

- `tools/test_hle_cop.sh` fails 5 checks: the native Boot ROM (HLE) charges 0-8% more cycles than the real ROM for the `COP #$F7` PPU load (and the line-blit status
  byte `$034A` differs). The real Boot ROM is correct; only the HLE cost model is off. Emulation is frozen, so this will be fixed in the HLE.
- ARM64 JIT crashes under QEMU (fine on real ARM64 hardware): use the interpreter there.
- The APU is not reset at hand-off from the Boot ROM (on purpose): a cartridge must reset-halt it before loading its own program (`docs/boot-handoff.md`).
- `TIMER_HBLANK_PERIOD` is master/4096 (about 3.8 scanlines), not one scanline.
- The dev/retail Boot ROM separation has not had an adversarial review yet; do not treat it as a security boundary for anything that matters.
