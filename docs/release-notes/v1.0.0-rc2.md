Second release candidate of ZeroPoint 1.0: the fantasy-console emulator (DEF88186 CPU, PPU, APU, DMA), **the real Boot ROM and the APU BIOS, now in the same zip as the
emulator**, and the matching toolchain ([ZPdevtools](https://github.com/Pomsky2011/ZPdevtools) `v1.0.0-rc2`, [ZPgameTemplate](https://github.com/Pomsky2011/ZPgameTemplate) `v1.0.0-rc2`).

**Core revision 14.** It adds battery save RAM for cartridges and nothing else: a cartridge without it is the revision 13 machine, so every ROM, movie (`.zpm`) and golden hash
that ran on revision 13 (rc1) still runs identically. Revision 12 and earlier ROMs/movies do not replay (revision 13 stretched the raster).

## What is new

- **Cartridge save RAM.** A game can have 1 KiB to 512 KiB of battery-backed SRAM at banks `$C0-$C7` (`zpbuild --save-size 8K`; the size is in the signed header). A new
  cartridge reads `$FF`; it survives resets and power cycles. The frontends keep it in `<rom>.sav` next to the ROM (`--save FILE`, `--no-save`), written every couple of seconds
  while it changes, with an atomic rename. A yank takes it with the cartridge; a Stop 'n' Swop cartridge has its own file. `docs/cart-save.md` has the whole spec.
- **Movies carry the save they start with** (a `.zpm` embeds it, so a replay is exact whatever your `.sav` holds, and never reads or writes the file). Movies without save RAM are
  the same bytes as before.
- **Dev Boot ROM: erase the save.** On a dev unit, holding all four shoulder inputs of player 1 (both bumpers and both triggers) while it boots erases the save RAM to `$FF`.
  The retail Boot ROM has no such code.
- **SDK:** `zp_save.h` (read/write helpers and a two-slot checksummed `zp_save_store` that survives a power cut) and `lib/zp_save.asm`; the game template keeps the hero's position
  in save RAM. `rominspect` shows a ROM's save size.

## What is in the assets

- `zeropoint-<platform>-v1.0.0-rc2.zip`: the frontends (`zeropoint_sdl`, `zeropoint_qt`) and the command-line tools, built by CI for Linux x86-64 and ARM64, macOS Apple Silicon and
  Intel, Windows x64 and ARM64, **with the Boot ROM and APU BIOS in a `bootroms/` folder beside them**:
  `zeropoint_sdl game.zpb --boot bootroms/bootrom.bin --apu-bios bootroms/bios_full.bin`. `SHA256SUMS.txt` has every hash.
- `zeropoint-bootroms-v1.0.0-rc2.zip`: the same `bootroms/` folder on its own (for an emulator you already have). `bootrom.bin` is the retail Boot ROM, `dev/bootrom_dev.bin` the dev one,
  `bios_full.bin` the APU BIOS; each file's hash is in `SHA256SUMS.txt` there, and `README.txt` says what each is for.
- The Boot ROM and APU BIOS are **binaries only** (the source is private) and are **in the public domain (CC0 1.0)**: do anything with them, including taking them apart
  (`bootroms/LICENSE.txt`). The retail `bootrom.bin` and `bios_full.bin` are byte for byte the ones from rc1; the dev Boot ROM is new (the save wipe).
- Without `--boot` / `--apu-bios` the emulator boots through its built-in HLE Boot ROM and APU BIOS (the HLE has no save wipe: delete the `.sav`).

## Notes for this build

- Linux builds need SDL2 (and Qt 6 for `zeropoint_qt`) installed. Zips lose the executable bit: `chmod +x` the binaries after unzipping.
- macOS builds are not signed or notarized and are not `.app` bundles; clear the quarantine flag (`xattr -dr com.apple.quarantine <folder>`) to run them.
- Minimum host: 2 cores, PassMark single-thread rating of 1500.
- The Qt and SDL frontends have not been run interactively on the 1/60 s frame (the frame pacer and offscreen Qt tests pass); the `.sav` handling is covered by tests of the shared
  `SaveFile` code and of the core, not by clicking through either window.
- Windows and macOS runtime for the serial TCP endpoint, the Qt Serial Console and the exception flow is untested (they build on every platform).

## Known issues

- `tools/test_hle_cop.sh` fails 5 checks: the native Boot ROM (HLE) charges 0-8% more cycles than the real ROM for the `COP #$F7` PPU load (and the line-blit status
  byte `$034A` differs). The real Boot ROM is correct; only the HLE cost model is off. Emulation is frozen, so this will be fixed in the HLE.
- ARM64 JIT crashes under QEMU (fine on real ARM64 hardware): use the interpreter there.
- The APU is not reset at hand-off from the Boot ROM (on purpose): a cartridge must reset-halt it before loading its own program (`docs/boot-handoff.md`).
- `TIMER_HBLANK_PERIOD` is master/4096 (about 3.8 scanlines), not one scanline.
- A save is not modelled for a dying battery or a power cut in the middle of a write (the SDK's `zp_save_store` is how a game stays safe).
- The dev/retail Boot ROM separation has not had an adversarial review yet; do not treat it as a security boundary for anything that matters.
